\begin{frame}{1. Hierarquia: GPU $\rightarrow$ SM $\rightarrow$ warp $\rightarrow$ thread}
\begin{columns}[T]
\column{0.52\textwidth}
\begin{tikzpicture}[x=1cm,y=1cm]
\draw[navy,thick,rounded corners=2mm] (0,0) rectangle (6.4,4.3);
\node[font=\scriptsize\bfseries,anchor=north west] at (0.1,4.15) {T4: 40 SMs, L2 4 MB, 16 GB GDDR6};
\draw[teal,thick,rounded corners=2mm,fill=pale] (0.2,0.2) rectangle (4.6,3.6);
\node[font=\tiny\bfseries,anchor=north west] at (0.25,3.55) {1 SM (Turing)};
\foreach \i/\y in {0/2.55,1/1.75,2/0.95}{
  \draw[navy,fill=white,rounded corners=1mm] (0.35,\y) rectangle (3.0,\y+0.7);
  \node[font=\tiny,align=left,anchor=west] at (0.4,\y+0.35) {bloco \i: 1 warp scheduler\\16 FP32 + 2 tensor cores};}
\node[font=\tiny] at (1.7,0.55) {+ bloco 3 (4 blocos por SM)};
\draw[navy,fill=white,rounded corners=1mm] (3.15,0.35) rectangle (4.45,3.25);
\node[font=\tiny,align=center] at (3.8,1.8) {96 KB\\L1 +\\shared\\[3pt]256 KB\\registr.};
\foreach \k in {0,...,5}{\draw[navy,fill=pale] (4.9,0.3+\k*0.55) rectangle (6.2,0.75+\k*0.55);}
\node[font=\tiny] at (5.55,3.8) {mais SMs};
\end{tikzpicture}
\column{0.46\textwidth}
\scriptsize
\begin{itemize}
\item \textbf{Kernel} = grade de \textbf{blocos}; cada bloco roda inteiro em 1 SM.
\item \textbf{Warp} = 32 threads que executam a mesma instrução (SIMT).
\item Cada \textbf{warp scheduler} escolhe, a cada ciclo, um warp \emph{pronto} e despacha sua instrução.
\item Um warp que espera memória ($\sim$centenas de ciclos) fica parado; o scheduler troca para outro sem custo. Isso é \textbf{latency hiding}.
\item Para esconder a latência é preciso ter \textbf{muitos warps em voo} (ocupação) e trabalho independente.
\end{itemize}
\nota{Fonte: NVIDIA Turing Architecture Whitepaper; T4 datasheet.}
\end{columns}
\end{frame}

\begin{frame}{1. Por que o decode batch = 1 é \emph{latency-bound}}
\begin{columns}[T]
\column{0.5\textwidth}
\scriptsize
\begin{itemize}
\item Cada passo depende do anterior: o token $t$ só existe depois do \texttt{argmax} do passo $t-1$. Não dá para paralelizar no tempo.
\item Com batch = 1, cada camada linear vira \textbf{GEMV} ($1 \times d$ por $d \times d'$): pouca matemática, muitos pesos lidos.
\item Kernels pequenos (RMSNorm, RoPE, residual, softmax) lançam poucos blocos: parte dos 40 SMs fica ociosa e há poucos warps para esconder latência.
\item Um passo de decode = \textbf{centenas de kernels} em sequência. O tempo por token é a soma das latências, não da vazão.
\end{itemize}
\column{0.48\textwidth}
\begin{center}
\begin{tikzpicture}[x=1cm,y=1cm]
\node[box,text width=2.1cm,font=\tiny] (p) at (0,0) {\textbf{Prefill}\\P tokens juntos\\GEMM $P\times d$};
\node[box,text width=2.1cm,font=\tiny] (d) at (3,0) {\textbf{Decode}\\1 token\\GEMV $1\times d$};
\node[font=\tiny,align=center] at (0,-1.0) {muitos blocos\\SMs cheios\\tensor cores úteis};
\node[font=\tiny,align=center] at (3,-1.0) {poucos blocos\\SMs esperando\\memória/CPU};
\end{tikzpicture}
\end{center}
\scriptsize
\textbf{Consequência para o benchmark:} o decode tok/s do projeto mede mais a \emph{latência de memória e de lançamento} do que a capacidade de cálculo da GPU. Mudanças pequenas de overhead aparecem direto no resultado.
\end{columns}
\end{frame}

\begin{frame}{2. Hierarquia de memória (T4)}
\begin{columns}[T]
\column{0.5\textwidth}
\begin{tikzpicture}[x=1cm,y=0.62cm]
\foreach \y/\w/\t in {4/1.4/{Registradores\\256 KB/SM},3/2.4/{L1 / shared\\96 KB/SM},2/3.4/{L2\\4 MB (todos os SMs)},1/4.6/{DRAM GDDR6\\16 GB, 300 GB/s}}{
  \fill[pale,draw=teal] (-\w/2,\y-0.95) rectangle (\w/2,\y-0.05);
  \node[font=\tiny,align=center] at (0,\y-0.5) {\t};}
\draw[arr] (2.9,0.1) -- (2.9,3.9);
\node[font=\tiny,align=left,anchor=west] at (3.0,2.0) {mais rápida\\menor\\mais perto\\do warp};
\end{tikzpicture}
\column{0.48\textwidth}
\scriptsize
\begin{itemize}
\item \textbf{Registradores}: privados de cada thread; o acesso mais rápido.
\item \textbf{Shared memory}: controlada pelo programador, compartilhada no bloco; é onde kernels de matmul fazem \emph{tiling}.
\item \textbf{L2}: cache comum a todos os SMs. Com 4 MB, não cabem os pesos de um modelo de 4B parâmetros: cada token lê os pesos da DRAM de novo.
\item \textbf{DRAM}: a T4 usa \textbf{GDDR6}, não HBM. HBM fica nas GPUs de datacenter maiores (A100, H100); a lógica é a mesma, só a banda muda.
\end{itemize}
\nota{Turing: os 96 KB por SM dividem-se em 32/64 KB de shared + 64/32 KB de L1 (whitepaper).}
\end{columns}
\end{frame}

\begin{frame}{2. Decode é \emph{bandwidth-bound}, prefill é \emph{compute-bound}}
\begin{columns}[T]
\column{0.5\textwidth}
\begin{tikzpicture}[x=1cm,y=1cm]
\draw[navy,->] (0,0) -- (5.2,0) node[below left,font=\tiny]{FLOP/byte (log)};
\draw[navy,->] (0,0) -- (0,3.2) node[above,font=\tiny]{FLOP/s};
\draw[teal,very thick] (0,0) -- (3.2,2.6) -- (5.0,2.6);
\node[font=\tiny,teal,anchor=south] at (4.1,2.6) {65 TFLOPS FP16};
\node[font=\tiny,teal,rotate=39] at (1.3,1.35) {300 GB/s};
\draw[dashed,navy] (3.2,0) -- (3.2,2.6); \node[font=\tiny] at (3.2,-0.25) {$\approx$217};
\fill[alerta] (0.6,0.49) circle (2pt); \node[font=\tiny,alerta,anchor=west] at (0.65,0.3) {decode};
\fill[navy] (4.4,2.6) circle (2pt); \node[font=\tiny,anchor=north] at (4.4,2.5) {prefill};
\end{tikzpicture}
\nota{Roofline simplificado. Ponto de equilíbrio = 65e12 / 300e9 $\approx$ 217 FLOP/byte.}
\column{0.48\textwidth}
\scriptsize
\textbf{Intensidade aritmética} (FLOP por byte lido):
\begin{itemize}
\item Decode: 2 FLOP por peso por token. Peso FP16 = 2 bytes $\Rightarrow$ $\sim$1 FLOP/B; peso 4-bit $\Rightarrow$ $\sim$4 FLOP/B. Muito abaixo de 217: a GPU espera a DRAM.
\item Prefill com $P$ tokens reusa cada peso $P$ vezes $\Rightarrow$ $\sim P\times$ mais FLOP/B. Prompts de centenas de tokens (3/5-shot) passam do equilíbrio: limite de compute.
\end{itemize}
\textbf{Conta de bolso (estimativa):} 4B parâmetros em 4-bit $\approx$ 2--2,5 GB lidos por token $\Rightarrow$ piso de $\sim$7--8 ms/token $\Rightarrow$ teto de $\sim$120--140 tok/s. Se o medido ficar muito abaixo, o gargalo é overhead (lançamento, Python, sync, dequant), não a banda.
\nota{O KV cache também é lido a cada token e cresce com o prompt: o 5-shot paga mais por token.}
\end{columns}
\end{frame}

\begin{frame}[fragile]{3. CUDA graphs e \texttt{torch.compile}}
\begin{columns}[T]
\column{0.5\textwidth}
\scriptsize
\begin{itemize}
\item \textbf{CUDA graph}: captura a sequência de kernels de um passo uma vez e depois relança tudo com \textbf{uma} chamada. Some o custo por kernel.
\item Exige formas e endereços fixos: o KV cache precisa ser \textbf{estático} (pré-alocado no tamanho máximo).
\item \texttt{torch.compile(mode="reduce-overhead")} gera kernels fundidos (Triton) e usa CUDA graphs.
\item Custos: compilação lenta nas primeiras chamadas e recompilação quando a forma muda. O warm-up precisa cobrir isso.
\end{itemize}
\column{0.48\textwidth}
\begin{codebox}
# KV cache fixo + forward compilado (HF)
model.generation_config.cache_implementation = "static"
model.forward = torch.compile(model.forward,
                              mode="reduce-overhead")
\end{codebox}
\scriptsize
\textbf{Cuidados neste projeto}
\begin{itemize}
\item Unsloth + bitsandbytes 4-bit + LoRA com \texttt{torch.compile} não tem compatibilidade garantida: testar num piloto antes.
\item Se usar, aplicar igual nos 4 modelos e nas 4 condições e registrar no manifesto; senão a comparação fica injusta.
\end{itemize}
\end{columns}
\end{frame}

\begin{frame}{4. Sincronização host-device}
\begin{columns}[T]
\column{0.5\textwidth}
\scriptsize
\begin{itemize}
\item CUDA é \textbf{assíncrono}: a CPU enfileira kernels num \emph{stream} e segue em frente; a GPU executa depois.
\item Pontos de sincronização (a CPU para e espera a GPU): \texttt{.cpu()}, \texttt{.item()}, \texttt{.tolist()}, \texttt{bool(tensor)}, \texttt{print(tensor)}, \texttt{torch.cuda.synchronize()}.
\item Sem sync, \texttt{time.perf\_counter()} mede quando a CPU \emph{enfileirou}, não quando a GPU terminou. Por isso \texttt{timed\_generate} chama \texttt{cuda\_sync()} antes e depois.
\end{itemize}
\column{0.48\textwidth}
\scriptsize
\textbf{No \texttt{generate} do Transformers} (lido no código da v5.20; confira a sua versão):
\begin{itemize}
\item Em CUDA, cada passo já faz \texttt{unfinished\_sequences.max() == 0} $\rightarrow$ \texttt{bool}: \textbf{1 sync por token}, com ou sem streamer.
\item Com streamer, no mesmo ponto: \texttt{streamer.put(tokens.cpu())}, ou seja, cópia D2H + chamada Python.
\item A versão que adia esse sync em 1 passo (\texttt{DeferredStopCheck}) só está ativa em MPS.
\end{itemize}
\nota{Enquanto a CPU espera o sync, ela não prepara o próximo passo. A GPU também fica parada nesse intervalo.}
\end{columns}
\end{frame}

\begin{frame}[fragile]{4. O custo do \texttt{TokenTimer} por token}
\begin{columns}[T]
\column{0.5\textwidth}
\begin{codebox}
def put(self, value):
    ids = value.tolist()            # D2H ja feito
    ...
    if self.is_prompt:
        if ids != self.prompt_ids:  # compara o prompt
            raise ValueError(...)
        ...
    self.ids.extend(ids)
    self.times.append(time.perf_counter())
\end{codebox}
\column{0.48\textwidth}
\scriptsize
\begin{itemize}
\item Por token: \texttt{.cpu()} + \texttt{tolist()} + checagens + \texttt{append}. São µs a dezenas de µs, somados aos $\sim$ms do passo e vezes 160 tokens.
\item \textbf{1º callback = prompt inteiro}: \texttt{input\_ids.cpu()}, \texttt{tolist()} e comparação de lista acontecem \textbf{dentro} da janela do TTFT. No 5-shot o prompt tem milhares de tokens, então o viés cresce com a condição.
\item O carimbo é o \textbf{relógio da CPU} quando o token chega no host. Inclui ruído do Python e do GIL; não é tempo de GPU.
\end{itemize}
\nota{A checagem de consistência é boa para correção. Na medição de velocidade, dá para movê-la para depois do \texttt{generate}.}
\end{columns}
\end{frame}

\begin{frame}{5. DVFS, clocks e warm-up}
\begin{columns}[T]
\column{0.5\textwidth}
\scriptsize
\begin{itemize}
\item \textbf{DVFS}: o driver muda o clock do SM e da memória conforme carga, temperatura e potência. Em repouso a GPU fica num estado de baixo clock (P8) e leva um tempo para subir.
\item A T4 tem TDP de \textbf{70 W} e refrigeração passiva: em rodadas longas ela reduz o clock por potência ou temperatura. A medição varia ao longo da campanha.
\item \textbf{Primeiras chamadas são mais lentas}: carga lazy de módulos CUDA, heurísticas do cuBLAS, crescimento do caching allocator, kernels do bitsandbytes e, com \texttt{torch.compile}, compilação.
\end{itemize}
\column{0.48\textwidth}
\scriptsize
\textbf{Hoje no projeto}
\begin{itemize}
\item Warm-up = \textbf{1 chamada de 8 tokens}. Ela é curta demais para estabilizar o clock e não exercita o tamanho de KV cache de 160 tokens.
\item A velocidade é medida logo depois da avaliação MedQuAD, então a GPU já chega quente. A 1ª condição de cada processo, não.
\end{itemize}
\textbf{Recomendado}
\begin{itemize}
\item 3 a 5 chamadas completas (160 tokens, prompt típico da condição) antes de medir; descartar.
\item Reportar mediana e IC, e checar se as primeiras perguntas são sistematicamente mais lentas.
\end{itemize}
\end{columns}
\end{frame}

\begin{frame}{6. Tensor cores na T4}
\begin{columns}[T]
\column{0.5\textwidth}
\scriptsize
\begin{tabular}{lr}
\toprule
\textbf{T4 (datasheet)} & \textbf{pico} \\
\midrule
FP32 (CUDA cores) & 8,1 TFLOPS \\
FP16 misto (tensor cores) & 65 TFLOPS \\
INT8 (tensor cores) & 130 TOPS \\
INT4 (tensor cores) & 260 TOPS \\
Banda DRAM & 300 GB/s \\
\bottomrule
\end{tabular}
\nota{320 tensor cores (8 por SM). Turing não tem BF16 nativo: Unsloth cai para FP16 (\texttt{is\_bfloat16\_supported()} = False).}
\column{0.48\textwidth}
\scriptsize
\begin{itemize}
\item Tensor core = unidade que faz um bloco de multiplicação de matrizes (MMA) por instrução de warp. Dá $\sim$8$\times$ o FP32.
\item \textbf{Prefill (GEMM)}: aproveita bem os tensor cores, e o TTFT escala com o tamanho do prompt.
\item \textbf{Decode (GEMV, M=1)}: o tile do tensor core fica quase vazio e o limite continua sendo a banda. Mais TFLOPS não ajudam, mas \textbf{menos bytes} ajudam.
\end{itemize}
\end{columns}
\end{frame}

\begin{frame}{6. Quantização 4-bit (NF4) e kernels de dequant}
\begin{columns}[T]
\column{0.5\textwidth}
\begin{tikzpicture}[x=1cm,y=1cm]
\node[box,text width=1.9cm,font=\tiny] (w) at (0,0) {pesos NF4\\0,5 byte/peso\\+ absmax por bloco};
\node[box,text width=1.9cm,font=\tiny] (r) at (2.9,0) {dequant\\em registradores\\(FP16)};
\node[box,text width=1.6cm,font=\tiny] (m) at (5.5,0) {GEMV\\ou GEMM};
\draw[arr] (w) -- node[above,font=\tiny]{DRAM} (r);
\draw[arr] (r) -- (m);
\end{tikzpicture}
\scriptsize
\begin{itemize}
\item \texttt{LOAD\_IN\_4BIT = True}: bitsandbytes NF4 (QLoRA). Cada peso ocupa 4 bits, com escala por bloco.
\item \textbf{Decode}: kernel 4-bit lê 4$\times$ menos bytes que FP16 e dequantiza no próprio kernel. Ganha banda, mas paga ALU de dequant, que vale a pena quando o gargalo é memória.
\item \textbf{Prefill}: em geral dequantiza a matriz para FP16 e chama a GEMM. É trabalho extra; o TTFT 4-bit pode ficar pior que o FP16.
\end{itemize}
\column{0.48\textwidth}
\scriptsize
\textbf{O que isso muda na leitura dos resultados}
\begin{itemize}
\item O decode tok/s mede \emph{kernel 4-bit do bitsandbytes + Unsloth}, não o modelo em si. Outra versão do bnb pode mudar o número.
\item Os adaptadores LoRA ficam em FP16 por cima do 4-bit: são matmuls extras por camada só na condição fine-tuned.
\item Alternativas para estudar (fora do protocolo atual): kernels 4-bit dedicados para decode (ex.: Marlin/AWQ/GPTQ), ou fundir o LoRA no peso antes de medir.
\end{itemize}
\nota{O caminho exato (gemv vs dequant+GEMM) depende da versão do bitsandbytes. Registre a versão no ambiente.}
\end{columns}
\end{frame}

\begin{frame}[fragile]{7. Tempo de GPU com CUDA events (sem streamer)}
\begin{columns}[T]
\column{0.58\textwidth}
\begin{codeboxtiny}
from transformers import LogitsProcessor, LogitsProcessorList

class EventTimer(LogitsProcessor):  # 1 evento CUDA por passo, sem sync
    def __init__(self):
        self.events = []
    def __call__(self, input_ids, scores):
        ev = torch.cuda.Event(enable_timing=True)
        ev.record()
        self.events.append(ev)
        return scores
@torch.inference_mode()
def gpu_timed_generate(model, question, max_new_tokens):
    _, prompt = build_prompt(question)
    inputs = encode_prompt(prompt, max_new_tokens)
    timer = EventTimer()
    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    cuda_sync()
    start.record()
    model.generate(**inputs, min_new_tokens=max_new_tokens,
        max_new_tokens=max_new_tokens, do_sample=False, use_cache=True,
        pad_token_id=text_tokenizer.pad_token_id,
        logits_processor=LogitsProcessorList([timer]))
    end.record()
    cuda_sync()
    ms = [start.elapsed_time(ev) for ev in timer.events]
    return {"ttft_gpu_s": ms[0] / 1000,
            "total_gpu_s": start.elapsed_time(end) / 1000,
            "decode_tok_s": (len(ms) - 1) / ((ms[-1] - ms[0]) / 1000)}
\end{codeboxtiny}
\column{0.4\textwidth}
\scriptsize
\begin{itemize}
\item O \texttt{LogitsProcessor} roda uma vez por passo, logo depois do forward. \texttt{ev.record()} só enfileira um marcador no stream, sem sync extra.
\item \texttt{elapsed\_time} usa o relógio da GPU (ms). \texttt{ms[0]} $\approx$ fim do prefill = TTFT de GPU.
\item Os buracos causados pela CPU continuam contando. Isso é correto: é latência real. O que sai é o ruído do Python do streamer.
\item Rodar \textbf{depois} do warm-up:
\end{itemize}
\begin{codeboxtiny}
q = speed_questions[0]
for _ in range(3):  # warm-up, descartado
    gpu_timed_generate(model, q, 160)
\end{codeboxtiny}
\nota{Não executado aqui (sem CUDA). Validar no Colab T4 comparando com o \texttt{TokenTimer}.}
\end{columns}
\end{frame}
